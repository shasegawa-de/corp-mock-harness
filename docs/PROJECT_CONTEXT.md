## 1. プロジェクトの目的

企業のコーポレートサイト、営業資料、SNS、バナー等で使う、端末モック画像のアートディレクションを再現可能にする。生成モデル固有の単発プロンプトを増やすだけではなく、**端末仕様・端末姿勢・配置・建築的な背景・素材・照明・採用済みリファレンス・品質検査を管理し、良い構図を再利用しながら新案を探索する**ことが目的。

- 対象端末：**標準 iPhone 17（ブラック、Proではない）**と**MacBook Pro 14インチ（開いた状態）**。端末単体またはMac＋iPhoneの2台構成。
- 端末0台の **environment-only** も製品モックとは別の正式カテゴリ。壁、床、建築面の接合、展示ブロック、素材と照明の比較に用いる。
- 実行環境は ChatGPT の画像生成や Nano Banana 等を想定。ハーネス自体には画像生成 API や実行プログラムを必須としない。HTMLカタログと GitHub は共同利用・検証のための資産。
- 探索と定番再利用を分離する。**既存の良い構図は完成プロンプトを1本ずつ使う**。新構図を探索するときだけ設定を組み合わせ、良かった結果をレビューしてからライブラリに追加する。
- 生成品質・見た目の好み・厳密な筐体再現・生成ツールに渡されたプロンプトの一致は**別々に評価**する。プロンプトが存在するだけでは「検証済み」としない。

## 3. ビジュアルの共通契約（変えてはいけない基準）

- **一回の画像生成＝16:9横長の独立した1写真・1カメラ視点。** 2×2グリッド、コンタクトシート、複数カメラ視点の合成画像は不可。1写真内の端末数は指示に従い0・1・2台。
- iPhoneは**標準17・黒・フラットな筐体・中央Dynamic Island**。Macは**14インチ・正確なキーボード／トラックパッド／画面ノッチ・常に開いた状態**。Mac全体を閉じたり寝かせたりしない。
- 端末がある場合、**すべての画面は全面が見える純白・無地**。画面内のUI、文字、反射による目立つ着色、追加端末、人物、手、メーカーのロゴ、透かしは不可。
- 背景は**無彩色〜ハーフグレーの抑制された建築空間**。マイクロセメント、ファイバーセメント、珪藻土・プラスター、コンクリート、スレート、スモークガラス、金属、白系／チャコール系の控えめな大理石を建築面として使う。床・壁・角・目地には物理的な整合性が必要。建築面は概ね0〜3面に抑える。
- 光は柔らかいスタジオ光と自然な反射・接地影。過剰な斜光ビームや不自然な巨大な影は避ける。
- **木目の机、家具、観葉植物、コーヒー、文房具、装飾用の積み木、展示に無関係なスタンド／小道具は不要**。ただし意図的な展示台を指定した on-block に限り、鉱物系の単純な支持体を許す。
- カメラは**画面と筐体を正しく見せるために動かす**。一般的な俯瞰・90度真上からの撮影は廃止。例外として、寝かせたiPhoneでは画面が見える**床・天面に対して斜め上40〜55度**の視点を使う。

## 4. 端末姿勢と空間モード

### iPhone 17単体

- **立て置き：** 正面または緩い三方向視点、4隅が見える白画面。
- **床に寝かせる：** 画面を上向きに床へ接地。カメラを斜め上に移動し、薄い側面と画面の両方を写す。
- **床で傾ける：** 壁や一体の建築面に自然に支持された姿勢。空中で不自然に自立させない。
- **ブロックに寝かせる：** **小さな立方体は不可**。iPhoneより充分に広い**テーブル程度の水平天面（目安80〜140cm幅）の単一鉱物系ボリューム**を使う。机や脚付きテーブルは不可。
- **ブロック上で傾ける：** 統合された面や背面支持で物理的に成立させる。カメラを傾斜画面に合わせる。
- **空中浮遊：** 床なしの suspended を優先。浮遊でも画面4隅が視認できる姿勢。

### MacBook Pro単体・Mac＋iPhoneの2台構成

- Macの画面は必ず立ち上げ、**キーボードとトラックパッドを見せる**。Macのベースが床や台に水平に接するのはよいが、「Mac全体を寝かせる／閉じる」は禁止。
- 2台構成は**Mac1台＋標準iPhone1台**。左右配置または奥行き差を作る。iPhoneでMacの画面やキーボードを隠さない。実物の相対スケールを崩さない。

### 配置・背景の4モード

| モード | 意味 | 絶対条件 |
|---|---|---|
| grounded | 床へ直接接地 | 連続した鉱物系の床、自然な接地影 |
| on-block | 建築的な鉱物系展示台へ接地 | 実際に端末を支え、不要な飾りのブロックは置かない |
| hover | **床が見える**低い浮遊 | 床と離れた弱い影で高さを表現 |
| suspended | **床が画面内に一切見えない**空中浮遊 | 床・床壁の交線・地平線・床への投影影・台座なし。縦の建築面と階調で奥行きを作る |

ユーザーレビューでは、床が強調された浮遊より**床のない suspended**が好評。hover を suspended の代用にしない。

## 5. 端末なしの建築環境／素材研究

- environment-only は **devices=[]** であり、写真内にも電子機器を置かない。
- 建築面は「素材マクロ写真・平面テクスチャのスウォッチ」ではなく、**壁や床として施工された状態**を描く。角・目地・壁床の接合が分かる。
- 床面重視の作例は**フレームの約80〜85%が床**。低い斜め方向のカメラ、背景の壁は最小限。
- 対象：マイクロセメント壁／床、ファイバーセメント壁、珪藻土・プラスター、ガラスと石材の接合、サンドブラストコンクリート床、チャコール壁床、白系・グラファイト系の**控えめな石目の大理石**。
- 大理石は抜け漏れの指摘を受けて追加された重要素材。壁・床・幅広の単一展示ブロックとして使用。極端な白い稲妻状の石目や過度な鏡面仕上げは避ける。
- 環境だけの背景・照明プロンプトは [prompts/environment/](../prompts/environment/)、施工スケールの壁・床は [prompts/architectural-surfaces/](../prompts/architectural-surfaces/) にある。紐づけは configs/presets.json の surface_studies 等。

## 7. 既知の失敗と再発防止

1. **4画像の指示が2×2コラージュに化けた。** 4回独立して生成したつもりでも、画像ツールに渡った指示自体が複数コマ構成になっていた事例がある。単純に生成モデルの品質が悪いのではなく**ツールへのプロンプト引き渡しのドリフト**。[検証記録](../history/2026-10-19-prompt-drift-regression.md)。
2. **Macだけを生成する依頼なのにiPhoneが混入した。** 完全な個数制約の明示と、出力画像での個数チェックが必要。
3. **床なし浮遊なのに床面と落ち影が大きい。** suspended は床・接合線・地平線・床影を一切許容しない。
4. **素材の不一致。** スモークガラスが不透明なコンクリートに見える、ファイバーセメントが粗すぎる、建築面の作例が単なる接写になった、大理石が素材群から抜けたなど。
5. **作例カタログの画質・出自の混在。** 低解像度の切り抜きや再構成画像を完成プロンプトの「生成結果」と誤認しない。画像とプロンプトの対応・品質を必ず明記する。
6. **画像ツールが単独背景ではなくカタログのボード全体を生成したことがある。** 画像生成には**1写真・1シーンだけ**を指示。HTML/UIの文脈や複数案を同じ画像プロンプトに混入させない。
7. **HTMLの構造不備とUI粒度の不統一。** 過去に埋め込み画像やカード表示の破損があり、ナビゲーションで「端末／配置／素材／評価」が同列だった。表示とフィルターを別々に検証する必要がある。

### 生成時の最小QA

- 4つの正本ファイルをGitHub mainから全文取得する。ZIP不使用。
- **1シーンの最終プロンプト**を固定し、画像生成ツールを**1回だけ**呼び出す。ツール側の実効文面が取得可能なら照合する。逸脱時は PROMPT_DRIFT。見えなければ PROMPT_UNVERIFIED。
- 出力画像で16:9、端末数、筐体、純白画面、全画面可視、支持の物理的成立、床の有無、建築面・材質・光、余分な小道具を判定。
- 出力画像の品質は PASS / REJECT / UNVERIFIED で独立判定。プロンプト文字列を固定できたことと画像の合格を混同しない。
- 詳細判定は [templates/review.md](../templates/review.md) を使い、**好評の方向性**と**検証済みの完成画像**を混同しない。

## 8. HTMLカタログの設計方針と未完了タスク

正本：**[catalog/index.html](../catalog/index.html)**（main、約4MB級の比較的大きなHTML）。画像と完成プロンプト、コピー、画像拡大、一覧表示が主目的。[GitHub Pagesの公開カタログ](https://shasegawa-de.github.io/corp-mock-harness/)で閲覧できる。公開処理は[.github/workflows/pages.yml](../.github/workflows/pages.yml)で管理し、mainの`catalog/`・`assets/`・同ワークフローの更新時に`catalog/`をそのまま自動配信する。カタログの正本は移動・複製しない。GitHubのコードビューはHTMLをレンダリングしないため、ローカル閲覧ではHTMLをダウンロードして開く。

### UI設計で決まったこと

- **第1階層＝対象カテゴリ：** すべて／iPhone 17／MacBook Pro／Mac＋iPhone／環境のみ。
- **第2階層＝絞り込み属性：** 配置（床置き・ブロック・浮遊）／素材（大理石等）／評価（採用方向・改善中・参考／要検証）。
- **検索欄は不要。** ユーザーはカタログ内の「構図・背景・素材を検索」等の文字検索UIの削除を明示的に希望。**前のセッションではGitHub上での削除完了を確認できていない。** 次にHTMLを編集する際は現物を検査し、検索UIが残っていれば入力欄・イベント・不要CSSを除去。フィルター条件のクリア操作は残す。
- フィルターの組み合わせ、件数表示、画像拡大、プロンプト全文・コピー、一覧表、モバイルの表示を壊さない。
- 大容量HTMLや埋め込み画像を再構築する際は、画像の破損・プレビュー差し替え漏れ・オンライン参照への依存を点検する。更新後は実ブラウザで最終確認する。
- **運用上の注意：** 過去に「HTMLの修正版」をチャット内のファイルとして渡したことがある。GitHub mainとの一致は毎回Git上のファイルと比較し、**ローカルファイルを更新しただけでGitHubに反映済みとは言わない**。

### 優先順位つきバックログ

**P0 — 直近**
1. カタログの不要な検索入力欄が残っているか確認し、あれば削除して動作検証・GitHubへコミットする。
2. カタログ画像を1枚ずつ監査し、「完成プロンプトどおりの独立生成」「コンセプト画像」「切り抜き」「再構成」を明確に区別。不一致画像を高品質な単独生成画像へ順次置換する。
3. 端末なしの壁・床・ガラス・大理石・床なし空間を、**各1シーンずつ**生成してQA。素材だけの接写やカタログ全体のボード出力は不採用。

**P1 — 継続改善**
4. 画像原本、生成時のプロンプト、使用モデル、QA結果をできるだけリポジトリに対応づける（プレビューと本番リファレンスを分離）。
5. HTMLのオフライン完結性・外部参照・ファイルサイズと読み込み速度を監査。大きくなりすぎる場合、画像を分離した構成を検討するが、オフライン要件を無断で破棄しない。
6. オプションのスキル・テンプレートに旧仕様が残っていないか監査。**AGENTS/STYLEと矛盾する個所は修正**する。
7. [STYLE.md](../STYLE.md) には「Background」と「Marble finishes」の見出しが同一行に連結された箇所がある（2026-10-20時点で確認）。Markdown上の整形を別タスクで修正する。視覚上の品質基準は変更しない。

**P2 — 設計課題**
8. 定番構図の「完成プロンプトを直接使用」と、新規探索の「4ファイル読込＋シーン設計」を分ける軽量実行モードを検討。**現在の必須4ファイル契約は合意なく変更しない**。
9. 採用済みの作例画像と、独立生成テスト／筐体検証の証跡を増やす。

## 9. 新しいチャット／Codexで再開する方法

### 2026-10-20：現行版の維持と次期版

- **[決定]** 現行カタログはユーザー確認済みとして維持。`catalog/index.html`の内容を変更せず、公開ルートも維持する。
- **[決定]** UIに依頼のないキャッチコピーや装飾的見出しを追加しない。文言は操作・条件・検証状態に必要なものに限定する。
- **[決定]** 全バージョンのトーン＆マナーを現行から変更しない。30件の画像・ギャラリー・一覧表を維持し、次期版も`catalog/index.html`を改変せず再利用する。
- **[却下]** 作例・一覧を消した独立した条件入力画面、別配色・別デザイン。比較と参照の体験を壊すため。TXT保存・プロンプト内訳・条件JSONのUIも不要として削除。
- **[前提修正]** 次期版の条件変更は各作例カード内で行い、元の画像とプロンプトを見ながら編集・全文コピーできる構成とする。元画像を変更後の生成結果とは扱わない。
- **[決定]** 次期版は条件の掛け合わせにプロンプトを連動させる。[Prompt Builder](https://shasegawa-de.github.io/corp-mock-harness/next/)を別URLに追加。対象・並び方・姿勢・配置・構図・建築面・素材・照明を扱い、矛盾する選択肢は連動調整する。
- **[未確認]** 新しい組立プロンプトの実画像品質と実効プロンプト一致。既存の採用状態を継承しない。画像生成は未実施。
- **継続ポイント：** [実装範囲と未確認事項](PROMPT_BUILDER.md)。既存バックログは現行版の継続課題として残し、次期版追加を理由に無断で修正しない。
