## 1. 北極星 — 何をよいデザインとするか

1. **参照・比較・判断ができることを最優先にする。** 作例カタログは「完成画像、撮影条件、元プロンプト、レビュー状態を比較する場所」。画像生成そのものや、多機能な編集画面を前面に出さない。
2. **必要な要素を見せ、不要な要素は削る。** 一つの役割に操作を重複させない。画像拡大、検索欄、案内文、装飾的カード、過剰なCTAなどは、実際の比較・判断に寄与しなければ置かない。「もっと機能を増やす」より認知負荷と迷いを減らす。
3. **既存の視覚品質と情報密度を崩さず改善する。** 新しい配色やトンマナへ安易に置換しない。ユーザーが支持したタグの形状・色・サイズ・選択状態、カード、画像の比率は理由なく変えない。
4. **UIの意味・状態・証拠を正確に表す。** 原画像／参考プレビュー、採用されたアートディレクション／画像QA、送信プロンプトの一致／未検証を混同しない。実行していない画像生成や公開を実施済みと見せない。
5. **変更は局所的、検証は全体的。** ヘッダーの修正でサイドバーやモバイルを壊さない。UIの変更後は実ブラウザで操作・キーボード・画像読込・レイアウトを確認し、成功した公開まで確認する。

上の5点は、このプロジェクトでの複数の個別レビューから整理した**運用上の原則**。個々の設定値は以下の採用決定を参照する。

### 実装の責務と変更禁止領域

- [catalog/index.html](../catalog/index.html) は**元のカタログ**。vNextの調整を反映するためにこの大きな原本を直接書き換えない。
- [scripts/render-next-catalog.mjs](../scripts/render-next-catalog.mjs) は原本からvNextのヘッダー／フィルター／カード列を構成。
- [catalog-next/style.css](../catalog-next/style.css) はヘッダー、タグ、モーダル等。 [catalog-next/left-sidebar.css](../catalog-next/left-sidebar.css) は左端のPCフィルター領域。 [catalog-next/filters.mjs](../catalog-next/filters.mjs) は9項目、依存関係、検索。 [catalog-next/app.mjs](../catalog-next/app.mjs) はカード→プロンプトモーダル。
- [catalog-next/engine.mjs](../catalog-next/engine.mjs) と [configs/presets.json](../configs/presets.json) は条件ID・ラベル・組合せのロジック。カタログ独自の互換性判定を増やさない。

## 3. 画像・モックの品質判断（UIとは別軸）

**ビジュアルの好みと、技術的な正しさと、生成経路の保証は別々の判定。** 最優先の厳密ルールは [STYLE.md](../STYLE.md) と [AGENTS.md](../AGENTS.md)。

- **単独16:9写真・一つのカメラ視点**。要求ごとに端末0／1／2台を厳守。ボード、2×2コラージュ、複数カメラは不採用。
- **端末あり**: 標準黒iPhone 17（Proではない）と／または開いたMacBook Pro 14。純白でUIのない全画面が見えること。端末比率を保ち、Macは画面・キーボード・トラックパッドが見える。寝かせたiPhoneは必要に応じ40〜55°の斜め上カメラを使う。
- **端末なし**: 壁・床・接合線・目地・光の構造を描き、デバイスや製品影を作らない。素材のマクロスウォッチではなく、建築スケールで施工された空間として成立させる。
- **素材と空間**: 無彩色〜ハーフグレー。マイクロセメント、繊維セメント、プラスター、白／グラファイト大理石等を整合した面に使う。大理石は細い自然な石目・抑えたサテン反射。強い装飾性や素材のすり替えは不可。
- **空間モードと支持**: groundedは接地、on-blockは必要な機能的鉱物ブロック、hoverは床が見える低浮遊、suspendedは床・地平線・床影・台座が一切ない浮遊。矛盾を許さない。
- **除外**: 木目机、家具、人物・手、植物、コーヒー、ロゴ、文字、小道具、不要な展示ブロック。自然な拡散光と柔らかい影を優先。
- **プロンプト経路**: 全4正本読込→単一シーンの英文を確定→1回の生成呼び出し→画像QA。ツールに渡った実効文面を見られない場合は **PROMPT_UNVERIFIED**。モデルが指示を書き換えたらPROMPT_DRIFTとして修正。厳密送信が必要なら専用のAPI/Actions経路を使う。

### 画像の状態を分ける

| 項目 | 何を確かめるか | 混同しないもの |
| --- | --- | --- |
| visual review | 人間が見た構図・素材・光がよいか | 筐体寸法やモデルへの実効入力の完全一致 |
| image QA | 画像の端末数、構造、画角、除外物、PNGの寸法等 | 画像が気に入ったという方向性の承認 |
| prompt fidelity | 生成ツールに届いた英文が固定した原文と一致したか | PROMPT_UNVERIFIEDはMATCHではない |
| binary provenance | 実際のPNG原本、SHA-256、登録先、ページの読込 | プレビューだけ／ZIPだけの登録 |
| publication | GitHub mainとPages上で個別PNGが読めるか | GitHubにQA記録があるだけの状態 |

2026-10-21時点で**4つの環境専用作例**（MR1 Carrara／MR2 graphite／TX1 microcement／TX2 fiber cement）はユーザーが視覚採用し、元PNGの個別登録とカタログ表示も検証済み。**画像が採用されたことは、生成時の実効プロンプト一致を証明しない**。原本のSHA-256と寸法は [approved-manifest.json](../assets/architectural-surfaces/approved-manifest.json)、レビュー経緯は [IMAGE_GAP_AUDIT.md](IMAGE_GAP_AUDIT.md) に記載。

## 5. 新規提案・レビューの手順

1. **どの問題を減らすのか**を一文で定義する（発見しにくい／迷う／誤認する／画像品質が不安定など）。条件追加やビジュアル変更そのものを目的にしない。
2. **今ある承認判断を確認**する。本書と現在のCSS／JSON／QAの差を確認し、既存の採用デザインを無断で変更しない。案と実装済み決定を混同しない。
3. **変更範囲を限定**する。UIならvNextの対象ファイルに絞り、画像生成の厳密ルールは正本4ファイルに従う。原本カタログを保全する。
4. **視覚的な検証項目と操作的な検証項目を分ける**（例:「白のまま」「カード型ではない」「クリックできる」「選択状態が保たれる」）。「おしゃれ」などの主観だけでは完了としない。
5. **回帰確認**: デスクトップ1280px、タブレット687px、スマホ390pxを基準に、横はみ出し、見出し、カード、9フィルター、絞り込み0件・クリア、サイドモーダル、キーボード操作、採用済み画像をチェックする。
6. **GitHub Actionsでテスト→GitHub Pages公開を確認**する。失敗した途中のワークフローは履歴に残る。最終実行の成功が確認できるまで「公開完了」と言わない。
7. **判断が確定したら記録更新**。採用／保留／却下、その理由、影響ファイル、検証状態、残った未確認点を書く。仕様値はコードに反映し、文書の値が古くならないよう同期する。

## 6. まだ確定していない論点

- 9フィルターの構造自体を減らすか。7項目＋条件付き詳細表示は**提案段階**。採用と書かない。
- 既存30作例のうち、MR1/MR2/TX1/TX2以外の原画像と実効プロンプトの全件照合は完了していない。すべてのカードを「完成検証済み」にしない。
- 撮影条件を変更したときの新規生成品質は未検証。候補カードは**一致条件の既存参照**であり、新画像の保証ではない。
- カタログを超える一括生成、運用自動化、追加デバイス等は別の企画・レビューとする。
